# X310 160 MHz master-clock experiment

On 2026-10-15, an isolated UHD build enabled a 160 MHz master clock on the
X310/UBX-160 v2 used with the XR1710G. **80 Msps OTA reception passed**, and
the live video link now uses this rate. 160 Msps decoded payloads but still
encountered sustained UE receive overflows.

## Clock implementation and verification

The build uses UHD source commit `2af4ddb9` and
[`tools/uhd-x310-160mhz.patch`](../tools/uhd-x310-160mhz.patch). The patch adds
exactly 160 MHz to the device-argument checks and the existing automatic PLL
branch. Normal PLL programming and initialization checks remain active.

The hardware probe reported:

```text
Radio 1x clock: 160 MHz
motherboard ref_locked: locked
requested=40000000  mcr=160000000 tx=40000000  rx=40000000
requested=80000000  mcr=160000000 tx=80000000  rx=80000000
requested=160000000 mcr=160000000 tx=160000000 rx=160000000
tx lo_locked: locked
```

These returned RX rates are configuration results; the RF tests below use
X310 TX and XR1710G RX. The patch does not establish X310 RX performance at
these rates. UHD still labels automatic master-clock configuration experimental.
Phase noise, images, and interface timing margin were not characterized.

The separate install on the X310 Linux host is
`~/uhd-x310-160m-20261015/install`; replace this example prefix on another
Linux host. The BS uses its library through
`LD_LIBRARY_PATH`; the original installed library, FPGA image and BS executable
were retained. The source archive lacks Git metadata, so the compiled version
string is `4.10.0.0-0-unknown`; the retained archive and patch identify the build.

To reproduce in a separate checkout, apply the patch at the UHD repository root,
configure `host/` with a separate `CMAKE_INSTALL_PREFIX`, and build/install there.
Launch the BS with that prefix's `lib` directory in `LD_LIBRARY_PATH` and
`master_clock_rate=160e6` in `usrp_device.device_args`. Stop any existing X310
owner before initialization. Returning to the stock library also requires
returning its master-clock argument to a stock-supported value.

## RF and payload measurements

Both ends used 2.350 GHz, FFT 1024, CP 128 and 100 symbols/frame. Payload bins
were +/-1 through +/-320, with the existing ten comb pilots and mid-frame
references. Uplink and ARQ were disabled. A local BS feeder offered 2,000
pseudorandom 512-byte UDP packets/s, or 8.192 Mb/s. Each received packet was
compared byte for byte with the expected sequence.

| MCR / sample rate | UE demod workers / RX queue | Steady window | Exact packets / sequence span | Corrupt received packets |
| --- | --- | ---: | ---: | ---: |
| 200 MHz / 40 Msps | 4 / 32 | 20 s | 40,004 / 40,004 | 0 |
| 160 MHz / 40 Msps | 4 / 32 | 20 s | 39,996 / 39,996 | 0 |
| 160 MHz / 80 Msps | 4 / 32 | 30 s | 59,990 / 59,994 | 0 |
| 160 MHz / 160 Msps | 4 / 32 | 30 s | 51,107 / 60,159 | 31 |
| 160 MHz / 160 Msps | 8 / 32 | 30 s | 57,374 / 60,013 | 3 |
| 160 MHz / 160 Msps | 8 / 128 | 30 s | 55,358 / 59,977 | 0 |

The denominator covers the first through last received sequence numbers;
startup and packets outside that interval are not included. These successive
short windows establish bounded observations, not long-duration delivery rates.
The eight-worker trials also reduced sync logging and enabled demod profiling,
so they are not a controlled comparison of worker count alone.

Separate three-second backend probes read approximately 80.011 and 159.971
million samples/s with no reported errors. Their short packetized measurements
identify the rate class, not sampling-clock accuracy. Sustained UE operation
at 160 Msps nevertheless reported receive overflows. The 128-entry trial
removed RX-frame-queue-full warnings during its observation but retained
metadata overflows; buffering alone did not resolve the remaining bottleneck.
No TX underflow was observed in the experimental BS logs.

A subsequent review of the independent `w1700k-stream` log found that its
published `lost` count increased from **530,778 to 534,975** during the
160 Msps intervals: **4,197 missing slices**, each representing 2,048 samples.
The surrounding reports advanced by approximately 391,000 slices per five
seconds, consistent with 160 Msps. Its `overruns` and `socket_drops` counters
remained zero. This establishes gaps already marked in the shared source;
it does not isolate export/network loss from receive-worker scheduling or
the publisher's reorder horizon. The backend maps both these `TAG_LOST` gaps
and reader-overwrite conditions to `RxError::Overflow`. Therefore the UE
overflow log alone cannot establish a slow UE reader or insufficient demod
compute. Per-cause counters and time-aligned source/consumer measurements are
needed to distinguish them. This review is retained in
`runtime/overflow-review-20261015/`.

Eight demod workers were confirmed on physical cores 8-15. At 160 Msps they
used roughly 45-50% CPU each; the receive thread used about 80%. Four LDPC
workers remained on cores 16, 18, 20 and 22. The high-rate work changed YAML
settings and launch configuration, using the UE's existing parallel pipeline.
Sensing queue and ZMQ publish drops were also observed and are distinct from
communication-payload delivery.

At fixed 40 Msps, switching MCR 200 to 160 MHz improved the measured broad
edge/middle amplitude statistic by about 8.2 dB, supporting the
[TX CIC droop diagnosis](edge-rolloff.md). Increasing sample rate also changes
the physical frequencies represented by each FFT bin; normalized-bin results
at different rates are not fixed-frequency filter comparisons.

## Live video profile

The running profile uses **80 Msps**, X310 MCR 160 MHz, XR band 0 at
2.350 GHz, 160 MHz analog filter, manual LNA 3 / LPF 8, and X310 TX gain
31.5 dB. The payload allocation spans 50 MHz. UE demodulation uses cores 8-15,
four LDPC workers and 128-entry frame/sync queues. PLL carrier correction and
the UE's frequency-observation ordering use the existing implementation.

The uploaded video loops as **1920x1080, 30 fps, H.264 at 30 Mb/s**, with AAC
at 128 kb/s and MPEG-TS paced to approximately **33 Mb/s**. Before that step,
20 Mb/s video produced 22.99 Mb/s of received TS in a 15-second window, zero
structurally invalid received datagrams, and an eight-second decoded segment
with no decoder errors. The first 30 Mb/s test received 32.86 Mb/s over a
30-second window, also with zero structurally invalid received datagrams.
TS structural checks alone cannot detect every lost or corrupt payload.

With the final video sender's MPEG-TS mux delay set to 0.7 seconds, a fresh
30-second receive window measured **32.858 Mb/s** and zero structurally
invalid datagrams. A later cumulative snapshot at 165.25 seconds contained
519,313 forwarded datagrams and **15 rejected TS datagrams**. A 20-second
remuxed segment decoded **585 video frames plus audio without decoder errors**.
The capture started between keyframes and initially lacked H.264 parameter
sets; its demux log also recorded a corrupt TS packet. The earlier full
30 Mb/s capture produced one H.264 macroblock decoding error. Thus the video
path is running at the higher rate, but the complete stream is not loss-free.
The live 80 Msps UE snapshot had zero backend metadata-error and RX-frame-queue
overflow messages, while mini-header failures and sensing output drops remained.

The video goes through the BS, RF link and UE to the configured player host
on UDP port `50001`. The constellation and sensing viewer connects to the
UE Linux host's IP using its existing ports. See [the playback command](../VIDEO_PLAYBACK.md).
